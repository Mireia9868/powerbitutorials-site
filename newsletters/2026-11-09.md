preheader: "PREVIOUSMONTH and DATEADD disagree by 10% on the 31st"

Last week was the fiscal year trap. This one is smaller, rarer, and harder to
notice — because it only shows up for a few days a year and looks correct the
rest of the time.

`PREVIOUSMONTH` and `DATEADD ( ..., -1, MONTH )` both claim to give you "the
previous month". On 31 March they give you different numbers:

```dax
-- Filtered to 31 March. This returns ALL of February.
CALCULATE ( [Total Sales], PREVIOUSMONTH ( 'Date'[Date] ) )

-- Filtered to 31 March. This returns 28 February only.
CALCULATE ( [Total Sales], DATEADD ( 'Date'[Date], -1, MONTH ) )
```

`PREVIOUSMONTH` returns a *month* — the whole thing, regardless of which day you
are standing on. `DATEADD` shifts your current date set by one month, so one day
maps to one day.

The rule that follows from that:

- **Month-over-month total** → `PREVIOUSMONTH`. You want February, all of it.
- **"The same day last month"** → `DATEADD`. You want 28 February, not all of it.

Get it backwards on a monthly total and March reads about 10% high, because you
compared 31 days of March against 28 days of February. April looks fine. May
looks fine. You find it in June.

## A 30-second check

Drop this into a card and filter a date in March:

```dax
MoM Drift =
VAR PriorMonthAll  = CALCULATE ( [Total Sales], PREVIOUSMONTH ( 'Date'[Date] ) )
VAR PriorDayShift  = CALCULATE ( [Total Sales], DATEADD ( 'Date'[Date], -1, MONTH ) )
RETURN
    PriorMonthAll - PriorDayShift
```

Zero means the two are equivalent on your data — which happens if your fact table
only has month-end rows, and is why the bug survives in some models and not
others. Non-zero means every month-over-month figure built on the wrong function
is off by exactly that amount.

Run it before you trust the MoM column. It takes less time than explaining the
number to someone.
